# Прогноз повітряних тривог по районах

Ймовірність того, що в районі **почнеться нова** повітряна тривога протягом 1, 3 або 6 годин.

> Це статистичний прогноз, а не офіційне оповіщення і не гарантія безпеки.
> Орієнтуйтесь на офіційні сигнали.

## Що це

Імовірнісний прогноз для 105 одиниць (райони; Запорізька й Тернопільська області та м. Київ — по
одній одиниці) на сітці щогодини. Ціль: чи почнеться нова районна тривога в (t, t + H], H = 1, 3, 6 год.
Модель навчена на офіційному каналі «Повітряна тривога» (11.2025–08.2026). Сервіс бере живі дані з
alerts.in.ua. Відповіді користувачу дає Telegram-бот (у розробці на гілці `feature/telegram-bot`).

## Головні результати

- **16 незахідних областей: GBM кращий за клімат** (частота тривог за «район × година тижня»).
  На test Brier skill 0.10–0.12, 95% CI від 0.09 до 0.15.
  - Обмеження: test оцінювали двічі. Гіперпараметри й калібрування обирались на validation.
- **GBM проти логістичної регресії.** На H = 1 / 3 GBM кращий, на H = 6 різниці немає. На зовнішній
  перевірці (alerts.in.ua) логістична регресія краща за GBM на всіх H.
  - Обмеження: зовнішня перевірка має інше визначення тривоги, тож це перевірка на зсув, а не
    якість на офіційних даних.
- **7 західних областей: модель не перемогла клімат,** тому сервіс там віддає клімат.
  - Обмеження: рішення ухвалене після другого перегляду test. Незалежної перевірки цього рішення немає.
- **Перевірки на витік і на розбіжність сервісу з офлайном** є тестами (див. таблицю нижче).

## GBM проти баз (Brier skill, 95% CI)

Brier skill = 1 − Brier(GBM) / Brier(база); більше за 0 — GBM кращий. Усі 105 одиниць. Повні
таблиці, зокрема для незахідних областей і бази «клімат + хвиля», — `reports/baseline_comparison.md`.

| validation | 3 | +0.087 [+0.073, +0.101] | +0.031 [+0.014, +0.049] |
| validation | 6 | +0.086 [+0.062, +0.110] | +0.015 [−0.017, +0.045] |

## Джерело даних і визначення тривоги — важливо

- **Модель навчена на офіційному Telegram-каналі «Повітряна тривога»** (@air_alert_ua,
  11.2025–08.2026). Там є лише сигнал «повітряна тривога» і «відбій».
- **Живі дані сервісу беруться з alerts.in.ua.** Це інше джерело з **іншим визначенням тривоги**:
  - крім «повітряної тривоги» (червоний рівень), воно містить «попередню загрозу» (жовтий рівень);
  - жовтих записів ~68%, і сервіс враховує обидва рівні;
  - точно зіставити рівні з офіційним сигналом не вдалося: канал мовчить з 07.09.2026, тож
    спільного періоду немає.
- **Офіційного API (api.ukrainealarm.com) не буде:** ключа немає.
- **Наслідок:** прогнози на живих даних мають зсув відносно того, що модель бачила в навчанні. На
  зовнішній перевірці (alerts.in.ua) частка тривог вища, ніж на офіційних даних (0.177 проти 0.122
  на H = 1). Ймовірності треба читати як орієнтир, а не як відкалібровану оцінку для alerts.in.ua.

## Живі дані: воркер

Окремий процес: опитує alerts.in.ua раз на хвилину й раз на добу робить знімок 30-денної історії
(точні кінці тривог). Дані пишуться в `data/live/alerts.sqlite`, стан — у
`data/live/worker_status.json`.

```bash
.venv/bin/python scripts/live_worker.py             # працює до SIGTERM / Ctrl+C
.venv/bin/python scripts/live_worker.py --health    # exit 0, якщо останнє опитування свіже (<5 хв)
```

Параметри задаються в `.env` / змінних середовища:
- `POLL_INTERVAL_S` (за замовчуванням 60);
- `ARCHIVE_EVERY_H` (24);
- `HEALTH_MAX_AGE_S` (300).

Файли для контейнера є, але їх не перевіряли — див. розділ «Docker (не перевірено)» нижче.

Ручні інструменти:
- `scripts/live_poll.py --once | --import-archive | --reconcile`;
- `scripts/archive_alerts.py`;
- `scripts/check_live_coverage.py` — показує діри в даних.

Кілька важливих поведінок:
- **Наближені кінці.** Тривога, що зникла з відповіді API, закривається моментом опитування
  (наближено); знімок історії замінює цей момент точним кінцем.
- **Обмеження історії.** Історія в API доступна лише за 30 діб: якщо воркер не працює довше,
  в архіві буде діра.
- **Офіційне API.** api.ukrainealarm.com не використовується: ключа немає й не буде (клас-заглушка
  `UkraineAlarmSource` лишився в коді, але не реалізований).

**Якщо воркер зупинений, сервіс не вдає, що дані свіжі.** Коли останнє опитування старше 10 хв:
- прогноз рахується **станом на останнє оновлення** (`as_of`) з `stale=True` і віком даних;
- `predict()` кидає `StaleDataError`, якщо явно не передати `allow_stale=True`.

## Docker (не перевірено)

`Dockerfile`, `docker-compose.yml` і `.dockerignore` написані під воркер:
- сервіс `worker`;
- том `./data`;
- секрети через `env_file: .env`, в образ вони не потрапляють;
- healthcheck через `--health`.

**Їх не збирали й не запускали: на машині розробки немає Docker.** Тому немає підтвердження, що образ
збирається, що контейнер працює і що healthcheck спрацьовує. Перед використанням це треба перевірити:

```bash
docker compose build
docker compose up worker
```

Перевірено лише запуск воркера напряму через Python: опитування, файл стану, `--health`, зупинка
на SIGTERM.

## predict()

```python
import pandas as pd
from src.service import predict, live_forecaster

now = pd.Timestamp.now(tz="UTC")

predict("Харківська область|Харківський район")      # -> {1: p, 3: p, 6: p} на зараз
fc = live_forecaster()
fc.forecast("м. Київ", now)    # + as_of, чи тривога активна, яка модель, вік даних, stale
fc.list_regions()              # 105 одиниць: "Область|Район" або "Область|*"
```

Регіон задається як `Область|Район`. Для м. Київ, Запорізької й Тернопільської областей можна
вказати просто назву області: їхні райони в даних ідентичні, тож це одна одиниця.

## Яка модель для яких областей

| Області | Модель | Чому |

| решта 16 (вкл. м. Київ) | **GBM**, калібрований на validation | на test Brier skill відносно клімату 0.10–0.12 (95% CI від 0.09 до 0.15, не перетинає 0); на зовнішній перевірці GBM кращий за клімат, але гірший за лог. регресію |

Якщо тривога вже активна, ймовірність на 1 год зазвичай низька: нова тривога можлива лише після

## Що не покриває зовнішня перевірка

Зовнішня перевірка — 22.09–15.10.2026, дані alerts.in.ua. Вона **не є** test і не означає, що
модель перевірена на живих даних:

- **Інше визначення тривоги.** Модель вчилася на офіційному каналі (лише «повітряна тривога»), а
  alerts.in.ua містить ще й «попередню загрозу» (жовтий рівень, ~68% записів). Точної відповідності
  рівнів не встановлено.
- **Відтворення живого режиму.** Перевірку побудовано з історії з точними кінцями тривог. Наближені
  кінці з опитувань і можливі пропуски полера вона не відтворює.
- **Період 29.08–22.09.2026.** Даних районного рівня тут немає (діра й 7-денний розігрів ознак).
- **Офіційні дані після 28.08.2026.** Офіційний канал мовчить з 07.09, тож якість на офіційному
  визначенні після test невідома.
- **Рішення щодо заходу.** Його ухвалено після двох переглядів test; зовнішня перевірка його не
  підтверджує, бо там інше визначення тривоги.

## Відтворення: одна команда

```bash
.venv/bin/python scripts/run_pipeline.py            # з наявних data/raw (якщо порожньо — завантажить)
.venv/bin/python scripts/run_pipeline.py --refresh  # спершу свіжі сирі дані (~16 хв через ліміт API)
```

Порядок кроків: сирі дані → очищення → мітки й розбиття → ознаки → навчання й калібрування на
validation → backtest → важливість ознак → експорт моделі сервісу → зовнішня перевірка → pytest →
`reports/pipeline_run.md`.

Розбиття й правило «захід — клімат, решта — GBM» зафіксовані в коді.

**Test пайплайн не оцінює:** test уже оцінено двічі й заморожено. Фінальний крок — лише вручну:

```bash
.venv/bin/python scripts/evaluate_final.py --part test --allow-test
```

Набір alerts.in.ua (зовнішня перевірка) залежить від знімків у `data/raw/alerts_in_ua`, тож після
`--refresh` він довший. Train, validation і test від цього не змінюються.
